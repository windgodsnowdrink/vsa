# 产品需求规划

设备需求
你是一位资深架构师，需要为我设计一套异地双主双活双集群的服务架构。当一个数据中心的集群出现异常时，另一个数据中心需在 30 秒内完成接替继续工作，且在这 30 秒的切换过程中，不影响设备正常运作以及用户正常的操作。
整套系统的关键信息。
终端设备列表

- OV400：设备事件上报终端，通过 sdk 对接架设在关键路口上方的智能摄像头，将车辆经过的事件 (包含结构化 json 数据和非结构化事件照片及短视频) 上报到系统平台。设计范围 1000 台，管控 16000 个智能摄像头。每次上报的过车数据包含结构化数据 0.3KB + 图片 500KB 以及视频 10MB。
- FC200：设备统计摄像头，架设在道路上方监控多条车道流量的智能摄像头，每隔 5 秒将车道的流量信息通过结构化的 json 数据上报到系统平台。约 2000 台，采购自第三方。
- SC300：红绿灯信号控制器，通过规则控制红绿灯的行为。可接收来自平台 TCP/UDP 发送的规则。 约 4000 台，采购自第三方。
- PS300: 道路流量引导屏，通过 TCP 连接接收平台发送的图片并展示在屏幕上。约 1000 台，采购自第三方。
  系统平台功能模块列表
  API 模块
- 接收来自 OV400 的过车事件和 FC200 上报的车道流量数据。将数据结构化之后发到 kafka 让逻辑服务消费处理。 每天产生 300 万 + 300 万的数据量。
- 需考虑过车事件包含了非结构事件的照片和短视频容易造成流量拥堵的情况。
- 建议 OV400 和 FC200 两种类型的 api 模块进行拆分。注意以后的扩展，不用每个设备一个 API 模块
- OV400 上报的数据需要将图片和视频通过对象存储持久化之后，把访问连接组装成进结构化信息里后再发到 kafka。
  过车分析模块
- 从 kafka 上消费 API 模块 OV400 的过车事件，进行逻辑处理后数据持久化。逻辑处理包括车牌识别、车辆颜色识别、车型判断等车辆特征提取，以及违法违规行为（如闯红灯、超速等）判定。
- 将分析后的违法事件推送至第三方平台。
- 将持久化数据进行统计，结合客户要求需要生成 BI 数据表。
  流量统计分析模块
- 从 kafka 上消费 API 模块的流量统计数据，进行逻辑处理后数据持久化。
- 按配置规则（如按区域划分、时间段设定等具体形式）定期将指定区域的 FC200 组合和指定时间的流量统计数据，交由算法服务（算法服务基于历史流量数据预测未来流量变化，进而判断是否需要调整信号灯规则）计算是否需要对路段进行信号灯进行规则控制。
- 通过调用物联服务模块下发信号灯规则控制规则给 SC300.
- 将持久化数据进行统计，结合客户要求需要生成 BI 数据表。
  物联模块
- 负责 SC300 和 PS300 等需要从平台反向控制的设备连接和管控等物联功能。
- 需解决服务故障造成所有设备不能管控的问题，可能的服务故障包括服务运行异常、网络异常。
  综合管理平台
- 展示 BI 数据
- 管控展示业务数据
- 管控设备
- 设置规则
- 其它系统管理常规功能（如用户权限管理、日志管理等）。
  技术栈约束
- 对象存储：请分析 MinIO 与 FTP+Nginx 组合的利弊，并给出最优选项。
- 消息中间件：Kafka
- 开发语言：NET10 环境 C#14
- 业务数据库：PGSQL, 用于保存常规的业务数据
- 时序数据库：TDengin，用于保存设备产生的记录数据
- 大数据处理技术：Hadoop + Hbase
- 集群管理：K8s
  其它信息和要求
- 两个不同城市的双集群，由同一网络运营商搭建了网络专线。请结合现场业务需求（如 OV400 上报数据量较大，包含 10MB 视频，且每天有 300 万条过车事件数据，FC200 每隔 5 秒上报一次流量数据，约 2000 台设备等），提出对专线带宽和延迟的要求。原始需求是客户希望整套系统不会因为系统不稳定或电、网、机房等因素影响系统正常运行，双集群是我们想到的方案，可以根据实际情况有其它方案。
- 数据同步机制要求实时同步，最好能利用数据库自身的机制进行同步，同步的数据范围包括业务数据（如 PGSQL 中的设备信息、用户信息、规则配置等）和设备记录数据（如 TDengine 中的设备产生的记录数据等）。
- 监控与告警要求：需监控各节点（服务器、存储设备等）的 CPU 使用率、内存占用率、磁盘空间使用率；各服务（API 服务、过车分析服务等）的响应时间、请求成功率、并发量；各终端设备的在线率、数据上报频率。当监控指标超过设定阈值（如 CPU 使用率超过 80%、服务响应时间超过 1 秒、设备在线率低于 95% 等）时，触发告警，告警方式包括短信、邮件、系统内弹窗，告警信息需包含异常指标、异常时间、异常节点 / 服务 / 设备标识，同时需明确告警处理流程（如一级告警需 15 分钟内响应，二级告警需 30 分钟内响应等）。
- 扩容与缩容策略：当服务并发量持续 30 分钟超过当前处理能力的 80%，或设备数量新增超过现有数量的 20% 时，触发扩容；当服务并发量持续 2 小时低于当前处理能力的 30% 时，触发缩容。扩容与缩容需支持自动和手动两种方式，自动扩容 / 缩容需在 10 分钟内完成节点或服务实例的增减，手动操作需提供便捷的操作界面。
- API 模块有图片和视频上传，需考虑流量限制和服务写文件的瓶颈。
  设计要求
- 输出单个集群的微服务架构方案。方案需体现出微服务治理、技术架构等关键信息，技术栈需根据设计要求进行细化。
- 输出避免单节点异常影响全局系统运行的部署实施方案
