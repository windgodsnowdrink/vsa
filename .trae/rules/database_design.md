# 数据库设计规划

1. 概述
   1.1. 标识
   本文档的标题：数据库设计规范
   本文档的标识：V1.0
   本文档的版本号：002
   1.2. 规范目的
   在许多信息管理系统项目中，建立大型规范的逻辑数据库是重中之重，系统的功能以及数据处理优化都跟数据库的设计有很大关系，如果设计妥当，开发者还能减少重复开发。

由此解决公司软件系统因技术、项目管理人员而在数据库表、字段等命名上存在不规范、不统一的情形。同时进一步规范系统在开发过程中对数据库、表、视图、字段等实体的命名规范，特制定本规范要求在后续系统开发或优化过程中严格按照本规范执行。
1.3. 适合范围
本文档是信息化建设项目公司内部数据库规范文档，适用于指导和规范各业务软件数据
库的设计和集成。本标准规定了数据库总体命名规范及数据库、表、表区分、字段、主键、
索引、外键、视图、存储过程、触发器、函数等命名需要遵循的要求，以及业务表在设计过
程中需要遵守的规范。
适用对象：开发、设计、测试、运维人员。

2.2. 注释要求
数据库、所有表，字段，触发器，存储过程，函数都要加详细的注释和说明。
2.3. 数据库命名规范
1：数据库名称只能用英文字母和下划线来组合。
2：项目上可使用系统名称代号来命名数据库，或使用系统名称的汉字拼音首字母来组合。
3：对于不同项目同一个系统，如果业务功能有部分差别，数据库名称+下划线+地区名；
2.4. 数据库表命名规范
一般表的命名约定：表名必须由 “子系统名（子系统标志）\_t_”做为前缀，和具体能
够清晰表达表数据内容的名称进行组合。
首字母组合。如 acc*t_yh：表示权限系统用户表。
数据字典表的命名约定：数据字典表名由“子系统名（子系统标志）\_d*”做为前缀、
和数据字典中文表名各个汉字英语的首字母（或英文）组成。如 acc*d_sblx：表示权限系统中设计的设备类型表。
视图名的命名约定：视图名由“子系统名（子系统标志）\_v*”前缀和视图名各个汉字英语的首字母（或英文）组成。
2.5. 表相关
2.5.1. 表空间
 1、数据表空间以 “tbs*+数据库名+data” 来命名。
 2、索引表空间以“tbs*+数据库名+idx” 来命名。
 3、临时表空间以“tbs*+数据库名+tmp” 来命名。
 4、回滚段表空间以“tbs*+数据库名+rbs” 来命名。
 5、LOB 段数据专用表空间以其数据表空间+*+lobs 来命名。如 tbs_vss_data_lobs。
2.5.2. 数据库表
 1、一般表的命名约定：由“系统名\_t*表义名”。
 2、数据字典表的命名约定：由“系统名*d*表义名”组成。
 地图表的命名约定：由“系统名*m*表义名”组成。
 3、视图名的命名约定：视图名由“系统名*v*视图表义名”
 4、临时表采用“系统名*tmp*+表义名” 格式构成。
 5、创建数据库表时，一定要加注释说明此表的意义。
 6、指定使用的数据表空间和索引表空间。
注：表义名均以其英语的首字符命名，表义名中英语和英语均采用小写，且字符间不
加分割符。如果出现与已有数据表对象命名重复的情况，可在新表名中适当增加中文名汉字
英语的韵母，避免重复。
2.5.3. 字段/列

- 1：不得直接使用"ID"作为列名。
- 2：采用有意义的列名，使用实际含义的英语首字符，且字符间不加任何分割符。
- 3：列名前后不加表名等作为前缀或后缀。
- 4：列名定义必须加注释。
  2.5.4. 主键定义
- 1：所有表都必须定义主键。
- 2：如果表只有一个字段则使用“表名 ID/表名 WYBS”来命名。
- 3：主键值对于主表一般不要直接使用 GUID，最好是有意义的一些数字。这是因为一般情况下，主键是聚集索引，善用主键为查询，比一般的索引字段都要快。使用 like 做主键范围查询时，最好是 xxx% ，不能是%xxx，因为后一种方式无法利用索引优势。
  2.6. 约束
  2.6.1. 主键约束
- 主键约束命名为：“PK*表名(或缩写)*主键标识”，如“PK_YHXX_YXID”等
  2.6.2. 外键约束
- 表外键命名为：“FK*表名(或缩写)*主表名(或缩写)\_主键标识”，如“FK_YHQX_YHXX_YHID”等
  2.6.3. CHECK 约束
- CHECK 约束命名为：“CHK*表名(或缩写)*列名（或缩写）”。
  2.6.4. UNIQUE 约束
- UNIQUE 约束命名为：“UNQ*表名(或缩写)*列名（或缩写）”。
  2.7. 触发器
  2.7.1. AFTER 型触发器
- 系统名*<表名>\_tr*[row]
  2.7.2. BEFORE 型触发器
- 系统名*<表名>\_tr_bef*[row]
  2.7.3. INSTEADOF 型触发器
- 系统名*<表名>\_ti*[row]
  2.8. 索引
- 索引的命名为：“IDX*表名（或缩写）*列名”。

3. 设计规范要求及建议
   3.1. 安全性设计
   3.1.1. 管理默认用户
   在生产环境中，必须严格管理 SYS 和 SYSTEM 用户，必须修改其默认密码，禁止用该用户建立应用数据库对象。删除或锁定默认安装但不使用的用户。
   3.1.2. 数据库级用户权限设计
   必须按照应用需求，设计不同的用户访问权限。包括应用系统管理用户，普通用户等，
   按照业务需求建立不同的应用角色。
   3.1.3. 角色与权限
   确定每个角色对数据库表的操作权限，如创建、检索、更新、删除等。每个角色拥有刚
   好能够完成任务的权限，不多也不少。在应用时再为用户分配角色，则每个用户的权限等于
   他所兼角色的权限之和。
   3.1.4. 应用级用户设计
   应用级的用户帐号密码不能与数据库相同，防止用户直接操作数据库。用户只能用帐号
   登录到应用软件，通过应用软件访问数据库，而没有其它途径操作数据库。
   3.1.5. 用户密码管理
   用户帐号的密码必须进行加密处理，确保在任何地方查询都不会出现密码的明文。
   3.2. 完整性设计
   采用数据库系统实现数据的完整性。这不但包括通过标准化实现的完整性而且还包括数
   据的功能性。
   3.2.1. NULL 值
   由于 NULL 值在参加任何运算时，结果均为 NULL，所以必须利用 IFNULL()函数把可能为
   NULL 值得字段或变量转换为非 NULL 的默认值。
   3.2.2. 触发器
   触发器是一种特殊的存储过程，通过对表的 DML 操作而触发执行，是为确保数据的完整
   性和一致性不被破坏而创建，实现数据的完整约束。选择触发器的 BEFORE 或 AFTER 事务属
   性的时候，对表操作的事务属性必须与应用程序事务属性保持一致，以避免死锁发生。在大
   量修改数据时，尽量避免使用触发器。
   3.2.3. 视图
   为了在数据库和应用程序之间提供另一层抽象，可以为应用程序建立专门的视图而不必
   非要应用程序直接访问表。这样做还为处理数据库变更时提供了更多的自由。视图是虚拟的
   数据库表，在使用时要遵循以下原则：
   1、为简化查询，将复杂的检索或子查询通过视图实现。
   2、提高数据的安全性，只将需要查看的数据信息显示给权限有限的人员。
   3、视图中如果嵌套使用视图，级数不要超过 3 级。
   4、由于视图中只能固定条件或没有条件，所以对于数据量较大或随时间的推移逐渐增
   多的表，不宜使用视图，可以采用实体化视图代替。
   5、除特殊需要，避免类似 SELECT _ FROM [TableName] 而没有检索条件的视图。
   6、视图中尽量避免出现数据排序的 SQL 语句。
   3.3. 数据字典设计要求
   以下是对数据字典的设计和命名进行规范要求。数据字典在设计上主键不能直接命名为
   ID，长度为 32/36 位，采用 GUID。为了更好的对字典数据进行识别，采用 XXXDM，名称
   则为 XXXMC。其它表主健在命名时同样不直接命名为 ID，采用 XXXWYBS/XXXID。
   表格 1 数据字典表设计规范（案例）
   | 属性名称 | 字段名称 | 说明 |
   |---------|---------|------|
   | 序号 | XH | 例：XXXXH,用于排序 |
   | 代码 | DM | 例如：XXXDM. 用于某种字典类型的编号；用做于主键。 |
   | 名称 | MC | 例如：XXXMC. 用于对编号的中文显示 |
   | 有效标志位 | YXBZW | 1：有效 0：无效 |
   各业务系统的数据表中必须要有如下 4 个系统预留字段：创建者 ID、创建时间、更新
   者 ID、更新时间四个字段，必须进行维护。即：插入新记录时同时维护创建者 ID、创建时
   间、更新者 ID、更新时间、四个字段；修改记录更新者 ID、更新时间二个字段.
   表格 2 普通业务数据表设计规范（案例）
   | 属性名称 | 字段名称 | 数据类型 | 说明 |
   |---------|---------|---------|------|
   | 创建时间 | CJSJ | TIMESTAMP | 系统预留字段 |

   3.5. SQL 编写
   3.5.1. 字符类型数据
   SQL 中的字符类型数据应该统一使用单引号。特别对纯数字的字符串，必须用单引号，
   否则会导致内部转换而引起性能问题或索引失效问题。利用 TRIM(),LOWER()等函数格式化
   匹配条件。
   3.5.2. 复杂 SQL
   对于非常复杂的 SQL（特别是有多层嵌套，带子句或相关子查询的），应该先考虑是否
   设计不当引起的。对于一些复杂 SQL 可以考虑使用程序实现。
   3.5.3. 避免 IN 子句
   使用 IN 或 NOTIN 子句时，特别是当子句中有多个值且表数据较多时，速度会明显下
   降。可以采用连接查询或外连接查询来提高性能。
   3.5.4. 避免使用 SELECT_ 语句
   如果不必要取出所有数据，不要用 \_ 来代替，应给出字段列表。
   3.5.5. 避免不必要的排序
   不必要的数据排序大大的降低系统性能。
   3.5.6. INSERT 语句
   使用 INSERT 语句一定要给出插入值的字段列表，这样即使表加了字段也不会影响现有
   系统的运行。
   3.5.7. 多表连接
   做多表操作时，应该给每个表取一个别名，每个表字段都应该标明其所属哪个表。
   3.5.8. 参数的传递
   SQL 语句的编写，变量尽量使用“?”绑定变量。
   3.5.9. 存储过程、函数中的注释
   示例如下：
   /\*
   目的：
   作者：
   创建日期：
   修改顺序号：
   修改者：
   修改日期：
   修改原因： （具体原因详细描述）
   /\*
   3.6. 其它设计建议
   1、表之间不要强制去遵守数据库范式设计，表字段设计时可充分考虑业务功能实现的
   简易性、性能等方面考虑进行，进行适当的冗余。
   2、不要使用 DDL 强制所有表之间进行主外键约束，尽量只针对核心业务表。考虑一
   定脏数据的冗余。
   3、尽量不要使用自增长列，特别是主键不允许使用自增长列。一个是在高并发下可能
   会存在错误，二个是在数据集群和数据同步时数据会出现不一致。
   4、尽量不要使用视图。
   5、尽量不要使用存储过程、触发器。
   6、建立或者修订数据库之后，必须用用户新输入的数据测试修改的字段。最重要的是，
   让用户进行测试并且同用户一起保证选择的数据类型满足要求。测试需要在把新数据库投入
   实际服务之前完成。
   7、让一个表专门存放一般数据库信息非常有用。在这个表里存放数据库当前版本、最
   近检查/修复、关联设计文档的名称、客户等信息。这样可以实现一种简单机制跟踪数据库。
