## 1. 背景与目标（Why）

### 1.1 业务背景
富士康系 PLC 边缘设备与 AIOT 平台规模化后，运维与运营团队需要在**统一内网控制台**中完成：设备资产值守、告警处置、吞吐/OEE 分析、全球分布可视化、社媒声量洞察与团队协作。此前的能力分散在脚本、临时看板与口头交接中，缺乏统一入口与连贯交互。

### 1.2 我们要解决的核心问题
1. **信息架构混乱**：导航按"数据类型"而非"用户任务"组织，8 项挤成一列，重点缺失（UX 诊断 B1）。
2. **交互连续性断裂**：地图点、活动流、告警、通知、抽屉地图等入口无法钻取到设备，形成 10 处体验断点（B3–B7、B10）。
3. **状态不可恢复**：刷新即丢失当前页与上下文，无法分享深链、无法顺畅交接班（B8）。
4. **搜索体验差**：输入即硬跳页、无结果数与空态（B9）。
5. **缺少主任务入口**：未决告警淹没在角落，无显眼处置入口（B10）。

### 1.3 产品目标（量化）
| 目标 | 指标 | 拟定基线 → 目标 |
|------|------|----------------|
| 缩短故障定位时间 | 未决告警平均处置时长（MTTR-定位段） | 现状未知 → ≤ 8 分钟 |
| 提升值守效率 | 告警→设备钻取一次成功率 | ≥ 95% |
| 降低交接成本 | 深链/刷新恢复成功率 | ≥ 99% |
| 统一入口 | 控制台日活覆盖运营/分析/治理三类角色 | 三类角色周覆盖 ≥ 80% |

> 注：基线为拟定值，需在 V1 上线后 2 周内用真实埋点校准（见 §10 指标）。

### 1.4 非目标（Non-goals）— 防止范围蔓延
- **不做面向公众的营销获客页**（内网场景，落地页已移除）。
- **不在 V1 接入真实 PLC/MQTT 生产数据**（V1 用 Mock + `/api` 种子数据，真实接入见路线图 Next）。
- **不做多租户 / 计费 / 工单计费**（处置工单为内部闭环，不涉及对外结算）。
- **不做移动原生 App**（V1 响应式 Web 覆盖移动端；原生 App 列入 Later）。
- **不做 BI 自助建模 / 自定义报表引擎**（V1 提供固定分析视图，自助分析列入 Later）。

## 4. 产品范围

### 4.1 In Scope（V1）
- 控制台 Web 外壳：侧边栏分组导航 + 顶栏（搜索/主题/通知/头像）+ 通知中心 + 全局设备抽屉。
- **运营监控组**（5）：驾驶舱、设备、告警、实时看板（PLC 3D 结构透视）、地图（全球分布）。
- **分析洞察组**（3）：统计、社媒矩阵、团队协作（Notion 风格）。
- **系统治理组**（2）：系统（健康/资源/边缘链路）、后端管理（插件/用户/主题路由/连接器）。
- 跨页钻取（`openDevice` 单一入口）、hash 深链与状态恢复、搜索结果下拉（防跳+空态）。
- 设计系统（亮/暗双主题、玻璃态、移动优先响应式）+ WCAG 2.2 AA 可达性基线。
- 后端演示 API（`/api/{resource}`）+ 静态托管（ASP.NET Core + Docker 容器化）。

### 4.2 Out of Scope（本期不做，见 §12 路线图）
- 真实 PLC/MQTT/SignalR 数据接入（Next）。
- 告警↔协作任务双向关联与自动工单（Next）。
- Blender MCP 高保真 3D 孪生替换程序化机架（Later）。
- 原生移动 App、RBAC 权限模型、审计日志（Later）。

## 5. 用户故事（标准格式）

1. **作为运营值守工程师**，我希望在驾驶舱看到未决告警数并一键进入处置页，以便缩短故障响应时间。
2. **作为设备工程师**，我希望点击地图园区点直接打开该设备详情并下发操作指令，以便快速定位与干预。
3. **作为运维主管**，我希望任何深层位置刷新或分享链接都能还原，以便交接班与远程协作顺畅。
4. **作为运营值守工程师**，我希望在告警页确认/解决后角标实时更新，以便掌握未决总量。
5. **作为数据分析师**，我希望在统计页看到吞吐/OEE 趋势，并能从协作任务关联到具体设备，以便从数据到行动。
6. **作为平台管理员**，我希望在后端管理统一管控插件/用户/主题路由/连接器，以便降低治理成本。
7. **作为移动端用户**，我希望在手机上不丢功能、仅改变导航形态，以便现场也能值守。

## 6. 功能需求规格（按三组模块）

### 6.1 运营监控组（Operate）

#### 6.1.1 驾驶舱（首页 / 总览）
- FR-OP-01 展示 4 个 KPI 卡片（设备在线率、今日采集点、活跃告警、AI 诊断命中率），含 ↑/↓ 趋势与进度条。
- FR-OP-02 展示 SVG 折线+柱状组合图（吞吐趋势 + 告警分布）。
- FR-OP-03 展示模拟实时活动流（订阅 `devices/.../#/telemetry` 逻辑一致）。
- FR-OP-04 **未决告警主任务横幅**：显示未决数，点击跳告警页并预置"活跃"筛选（修复 B10），支持键盘操作。
- FR-OP-05 活动流每条可点击 → 打开对应设备抽屉（修复 B4）。

#### 6.1.2 设备（资产清单 + 抽屉详情）
- FR-OP-10 设备卡片网格，支持按状态筛选与计数显示。
- FR-OP-11 卡片点击 → 全局设备抽屉，含 8 个 Tab：信息/心跳/操作/日志/指令/计划/任务/地图。
- FR-OP-12 抽屉「指令」Tab 可下发命令；「地图」Tab 提供「在地图中查看 →」跳转（修复 B7）。

#### 6.1.3 告警（FaultEvent 全生命周期）
- FR-OP-20 列表展示告警，状态含 活跃/已确认/已解决。
- FR-OP-21 行内「查看」→ 打开设备抽屉；「确认/解决」改写数据并实时更新侧栏角标（修复 B5）。
- FR-OP-22 支持按 `ctx.alarmFilter` 预置筛选（来自通知跳转）。

#### 6.1.4 实时看板（PLC 3D 结构透视）
- FR-OP-30 Three.js 程序化 PLC 机架（导轨 + 7 模块盒 + LED），模块状态着色 + 悬停 Raycaster 拾取联动遥测。
- FR-OP-31 预留 `GLTFLoader` 分支：生产级由 Blender MCP 导出 `.glb` 加载（见 §12 Later）。

#### 6.1.5 地图（全球分布 + 园区钻取）
- FR-OP-40 Three.js 全球 3D 地球（经纬线框 + 大气辉光 + 园区设备点按状态着色 + 郑州枢纽弧线）。
- FR-OP-41 园区点点击 → `openDevice` 打开设备抽屉（修复 B3）。

### 6.2 分析洞察组（Analyze）

#### 6.2.1 统计
- FR-AN-01 SVG 状态占比环图 + 吞吐折线 + 告警趋势柱状 + OEE 指标。
- FR-AN-02 从趋势可关联到具体设备（经 `openDevice`）。

#### 6.2.2 社媒矩阵（内网可见）

### 6.3 系统治理组（Govern）

## 7. 体验与设计要求

> 单一事实来源：`DESIGN.md`（设计系统）+ `UX-ARCHITECTURE.md`（体验架构）。

- **视觉**：科技天蓝 `#3b82f6` 主色、玻璃态 `blur(14px) saturate(140%)`、亮/暗双主题（暗色优先）。
- **可达性**：WCAG 2.2 AA（主按钮 `#2563eb` 白字达标、徽章文字 AA 安全深色、`focus-visible` 焦点环、`skip-link`、抽屉 `role=dialog`）。
- **交互原则**（必须遵守）：
  1. 三层操作上限（驾驶舱 → 模块 → 抽屉 Tab）。
  2. 单一设备入口 `openDevice`，禁止各自造弹窗。
  3. 状态可恢复（URL 深链 + 刷新还原）。
  4. 反馈即时（筛选/确认/搜索均有可见结果或状态变化）。
  5. 任务导向而非数据导向。
  6. 移动优先（窄屏不丢功能，仅改导航形态）。
- **微交互**：hover scale、active 收缩，仅 `transform/opacity ≤ .2s`；`prefers-reduced-motion` 全局降级。

## 8. 信息架构与导航

### 8.1 目标 IA（任务心智分组）
```
PLC·AIOT 控制台
├─ 运营监控 (Operate)   驾驶舱 / 设备 / 告警 / 实时看板 / 地图
├─ 分析洞察 (Analyze)   统计 / 社媒矩阵 / 团队协作
└─ 系统治理 (Govern)    系统 / 后端管理
```
- 分组上限 5 项（7±2 短期记忆），主路径置顶。
- 社媒/协作归入分析洞察，与日常值守解耦。

### 8.2 导航与状态模型
- 侧边栏（≥1024px 常驻）分组 + 图标；当前项左侧 3px 天蓝条。
- 移动端（<1024px）侧栏抽屉 + 顶部横向滚动胶囊导航。
- **深链**：`location.hash`（`#devices`、`#map/ZZ-A2-07`）；`navigate(page, deviceId)` + `replaceState` + `htmx.ajax` 换片；`hashchange` 支持前进/后退；`boot()` 恢复。
- **跨页上下文 `ctx`**：`{ deviceId, alarmFilter }`，落地到目标页。
- **全局设备抽屉**：`openDevice(id)` 唯一设备入口，任何页面可调用，关闭返回原页。

### 8.3 四条关键用户流（验收闭环）
- **流 A 告警处置**：通知 → 设备抽屉 → （地图 tab / 告警页确认解决）→ 角标 -1。
- **流 B 设备定位**：地图点 / 活动流 → 设备抽屉 → 操作/指令。
- **流 C 数据分析→行动**：统计 / 社媒 / 协作 → 关联设备 → 设备抽屉。
- **流 D 搜索**：输入 → 下拉命中（≤6 + 结果数/空态）→ 点结果开抽屉 / 「查看全部」跳设备页保持筛选。

## 9. 数据模型与接口

### 9.1 前端数据层（当前）
- Mock：`wwwroot/data/data.json`（18 键，覆盖全部页面）。
- 渲染：`wwwroot/js/app.js` 经 Axios 按页拉取并缓存，`htmx:afterSwap` 后按 `data-page` 渲染。

### 9.2 后端 API（演示，`src/PlcAiot.WebApi`）
- 技术基线：.NET 10 LTS + ASP.NET Core Minimal API。
- 端点：`GET /api/{resource}`，资源键：`dashboard / devices / alarms / statistics / realtime / map / system / admin / social / notion`；`GET /api/health`（探针）。
- 种子数据：`SeedData.json`（资源键子树，对应 `data.json` 结构）。
- 静态托管：`UseDefaultFiles` + `UseStaticFiles`，`StaticWebRoot` 可指向仓库 `wwwroot`；生产由领域服务 / PostgreSQL / MQTT 桥接替换。

### 9.3 边缘数据链路（§17.9，架构约束）
- **边缘库 SQLite**（EF Core + DapperAOT）：单文件 ACID、WAL 并发读、NativeAOT 兼容，存遥测缓存/设备注册表/离线消息缓冲。
- **边缘 MQTT Eclipse Mosquitto**：本地 pub/sub，`bridge` 把 `devices/#` 选择性转发中心 EMQX，形成"边缘自治 + 中心汇聚"双层 broker。
- **CommunityToolkit.Datasync**：离线优先增量同步（本地 SQLite ⇄ 中心 REST），内置冲突处理，适合设备注册表/配置类弱网数据。

### 9.4 MQTT 主题（九段）
`devices/{continent}/{country}/{province}/{city}/{district}/{line}/{batch}/{deviceId}/{type}`，服务端按 `type` 映射处理器（telemetry→时序库、alarm→告警、command→指令队列、heartbeat→存活、ai→诊断）。

## 10. 成功指标（北极星 + 驱动 + 健康）

### 10.1 北极星指标
**未决告警 30 分钟闭环率**（确认并解决占比）——直接反映"值守效率"这一产品核心价值。

| 地图/实时看板访问占比 | 可视化使用深度 | ≥ 25% |

| 指标 | 目标 |
|------|------|
| 首屏加载（FCP） | ≤ 1.5s（内网） |
| 深链/刷新恢复成功率 | ≥ 99% |

> 指标基线需在 V1 上线后 2 周内用真实埋点校准；当前数值为拟定。
