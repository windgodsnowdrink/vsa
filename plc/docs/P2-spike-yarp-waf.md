# P2 Spike：YARP 网关 / WAF 采用评估（ADR-111）

> 状态：Design Spike（未落地代码） · 阶段：P2/Later · 关联：ADR-108（内网免费）、ADR-111（Deferred→P2）
> 目的：明确 YARP 何时上、怎么布、与现有部署 / 限流的关系，避免在内网期过早引入一跳延迟与证书负担。

## 1. 现状（baseline）
- 无网关 / WAF 代码；SaaS 内网免费使用（ADR-108 裁定）。
- `plc-saas` 当前仅暴露 API：`/api/v1/*` + SignalR `/hubs/faults`；**尚无静态前端**（wwwroot 未建），故"前端静态路由"暂不成立。
- 全局限流已在 `plc-saas` 内有 `UseRateLimiter`（喂配额 429 故事）。

## 2. 拟采用方案（公网暴露时）
- **YARP 前置容器**：`/api/v1/*` → plc-saas；TLS 终止；全局限流中间件（与配额 429 对齐）；可选 `/` → 静态前端（待前端存在）。
- **WAF**：内网靠网络隔离 + YARP 请求大小 / 头限制即可；**ModSecurity 类 WAF 推迟至公网暴露**。
- **替代**：若部署前已有 nginx / traefik 入口，则省略 YARP，改在入口配置。

## 3. 迁移与风险
- 额外一跳延迟 + TLS 证书管理成本。
- 限流必须**复用** plc-saas 既有配额模型，避免在 YARP 与 App 双层重复限流导致语义错乱。
- 若前端未就绪，YARP 的静态路由段落闲置 —— 过早引入纯属负担。

## 4. 采用触发线（客观判据）
满足任一即建议启动：
1. **公网 / 多租户互联网暴露**（不再纯内网）；
2. 需要统一 TLS 终止 / 单入口收敛多个服务；
3. 命中合规要求（WAF / 审计）。

## 5. 开放问题
- **部署拓扑未定**：k8s Ingress？单机？云厂商 LB？直接决定"自建 YARP"还是"用现成 ingress" —— 这是本 ADR 最大前置依赖。
- 静态前端的存在时间与形态（决定 YARP 是否要管 / 路由）。

## 6. 建议
**暂不采用**。内网期靠网络隔离即可。先把部署拓扑定下来（决定 YARP vs nginx/traefik），并在前端就绪后再评估 YARP 静态路由价值。公网暴露前本 Spike 升格为实施方案。
